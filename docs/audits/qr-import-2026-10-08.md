# QR enrollment import review

## Acceptance contract

The owner clarified that URL means an otpauth://totp/ enrollment URL, not a URL to an image, and requested desktop Ctrl+V and phone keyboard Paste. The implementation accepts that URL in the existing manual key field and reads a locally selected or pasted QR image. The QR disclosure's editable paste field also accepts a setup URL. All paths validate the same TOTP provisioning data and apply its algorithm, digits and period before displaying codes. Existing Base32 input, masking, share links, reset, locale selection and theme behavior remain required.

The initial implementation mistakenly included external image retrieval. That unshipped path, its iframe, URL control, helper bundle and TLS test fixture were removed before publication. No external image request, proxy or automatic QR navigation is offered. The owner subsequently requested an image-oriented paste/upload surface and direct camera scanning. The dashed blue intake area now accepts paste and drag/drop, with separate file and camera actions.

The UI uses the adopted Space Grotesk tokens, Lucide icons and existing disclosure/button presentation. File selection uses the platform dialog. The disclosure contains a styled intake area/file trigger, camera action, nearby errors, loading status and a cancel action. Uploaded images and decoded QR text are not previewed; an active camera has a local video preview and Stop control. Empty, loading, success, invalid image, unsupported payload, multiple codes, unavailable decoder, permission/device errors, scanning, cancellation, reset and background transitions are acceptance states in both locales/themes and supported engines. Narrow layout, enlarged text and both page ends require opened screenshots.

## Research and design

The [Google Authenticator Key URI specification](https://github.com/google/google-authenticator/wiki/Key-Uri-Format) describes the enrollment URI inside a QR. The image need not be uploaded to an external decoder. The existing strict parser and Web Crypto HMAC remain the authentication path. QR decoding is transport of provisioned data, not key generation or a new OTP algorithm.

The [native BarcodeDetector API](https://developer.mozilla.org/en-US/docs/Web/API/BarcodeDetector) has incomplete browser coverage. A native-only path would exclude supported engines. The self-hosted [zxing-wasm reader](https://github.com/Sec-ant/zxing-wasm) supplies a common decoder. Its documented locateFile override replaces the default CDN with a same-origin WASM asset. The registry checked on 8 October 2026 reports latest and selected zxing-wasm 3.1.5, MIT, with no declared engine/peer restriction. Its matching ZXing-C++ source is 2ecec3f5be0ee803f6e14a5a2c7028c0cfe525b4 under Apache-2.0. Original upstream license texts and immutable source pointers are preserved and checked in the build.

The reader is loaded on image import or camera scanning. Ordinary Base32 and pasted-URI calculation do not load its optional JavaScript/WASM. Main-thread browser image decoding and Canvas rasterization work across Chromium, Firefox and WebKit; an ephemeral worker runs QR decoding with a 15-second cancellation limit. A worker-only image decode path was rejected after WebKit compatibility failures. Work is bounded to 20 MiB, 24 million pixels and 12,000 pixels per side, then resized to a 4096-pixel longest side. These are workload limits, not proof against every browser decoder vulnerability. PNG/GIF header dimensions are checked before browser decode; JPEG/WebP dimensions are checked afterward.

Only one QR with a valid TOTP setup URI is accepted. HOTP, ordinary web URLs, arbitrary text, migration exports, duplicate recognized parameters and multiple symbols are rejected. Payloads are never navigated or fetched. CSP allows same-origin assets, denies frames/form submissions and external Fetch, and permits only WebAssembly compilation rather than JavaScript eval. Worker pixels and Canvas resources are released after reading. JavaScript strings and browser internals cannot be securely erased.

Revision guards prevent a cancelled or stale image read from overwriting later manual edits. Starting a read clears the previous visible code/share link until completion. Failed reads preserve the manual key and resume calculation. Manual edits, settings changes, reset, tab hide and page exit cancel pending work. Pasted setup URLs use the original local parser without any image download.

The [native paste event](https://developer.mozilla.org/en-US/docs/Web/API/Element/paste_event) exposes user-pasted data through clipboardData. The QR disclosure handles this event instead of calling asynchronous clipboard read APIs. An editable, visually masked text field allows phone keyboard Paste and handles input delivery without a ClipboardEvent. It rejects multiple files and clears transient values. Synthetic ClipboardEvent and input fixtures exercise the browser-facing code path and prohibit read/readText calls. Firefox's synthetic event constructor discards the supplied DataTransfer in the tested build; the fixture explicitly installs its own clipboardData property, without changing application behavior. These fixtures do not prove native image delivery by every phone keyboard or operating system. Unsupported image paste has the local-file alternative.

The [getUserMedia API](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) requires a secure context and browser permission. The explicit camera action requests audio false and ideal rear-facing video, then shows a muted inline preview. It never uses MediaRecorder, a peer connection or upload. Frames are reduced to a 1280-pixel longest side and decoded sequentially with one worker per scan session and a pause between reads. An empty frame continues scanning; invalid or ambiguous provisioning data stops with an error. The camera has a two-minute deadline after access is obtained. Success, failure, Stop/Escape, edit, reset, disclosure close, backgrounding and page exit stop every delivered track, detach the preview and terminate decoding. If permission arrives after cancellation, that stream is stopped before use. [MediaStreamTrack.stop](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/stop) releases this application's track; the page cannot revoke the browser's stored permission or control another application using the camera.

## Verification status

Local verification on Windows on 8 October 2026 used Node 24.21.0, npm 12.2.0 and the locked toolchain. The corrected acceptance contract passed:

- Source type, lint, CSS, formatting and standards checks; 39 Astro files with no errors, warnings or hints; six original license texts in source and build.
- 30 unit tests, including official RFC 6238/RFC 4226 vectors, an independently implemented HMAC reference and QR input boundaries.
- 294 browser cases on Chromium, Firefox and WebKit, with zero retries and zero skips; 81 cases cover QR transport, images, paste/drop, URI parsing, camera, cancellation and failures. Shared header/footer checks passed 156 cases. After the final placeholder and camera deadline lint refinement, all 42 affected camera/disclosure cases passed again without retries or skips.
- Native Chromium Control+V with both a PNG clipboard fixture and a setup URL, producing the official public RFC result. Application clipboard read/readText APIs are also prohibited by the synthetic paste fixtures.
- Native Chromium getUserMedia with a fake video device containing public QR frames, producing the same official result and detaching the preview afterward. Cross-engine camera tests explicitly replace acquisition and video-frame delivery but run the actual raster, worker, parser and OTP path. Windows WebKit automation exposes neither MediaDevices nor MediaStream; providing these fixture boundaries tests lifecycle behavior and does not claim native camera support in that build.
- Opened screenshots for both languages and themes, all three engines, desktop and narrow layouts, and 320-pixel width with text enlarged to 200%. Screenshots include page ends, import controls, loading, success and field-local errors.
- Built same-origin decoder metadata, WASM bytes/hash, CSP and license checks; runtime dependency audit with zero reported vulnerabilities.

Earlier results for the discarded image-URL design are not acceptance evidence for this contract. Browser automation and visual inspection are project checks, not independent security review or proof of physical phone keyboard behavior.

## Controlled lab performance

The original c3ce5dc7295ba69650fae3aa1aea911bd3432a3e build was archived separately before measurement. Existing dependency versions were unchanged when adding the QR decoder and fixture packages. Before and after each used the same Node and Chromium installation, cold Lighthouse navigation, both languages, three mobile and three desktop runs per language, and no concurrent test suite. Mobile simulation used 390x844, 150 ms latency, 1.6 Mbps and 4x CPU; desktop used 1440x900, 40 ms, 10 Mbps and 1x CPU. Raw reports and summaries are retained under local output/lighthouse and the archived baseline output tree.

All runs meet the existing LCP 2500 ms, CLS 0.1 and TBT 200 ms budgets. Mobile median LCP increased about 76-90 ms in this pair of builds; these short lab runs do not establish field performance or a statistical causal estimate. The final after build includes the styled intake area and camera controls. The optional decoder is not requested on ordinary key/URI use. Three separate, unthrottled localhost first-import probes took 107, 105 and 106 ms with a public 480-pixel QR fixture and no parallel test suite. They are exploratory latency measurements, not a baseline comparison or phone latency claim.

## Publication verification

Exact-head CI and deployed-site verification are required after the authorized source push. This local review does not stand in for those publication gates. The existing Pages workflow checks Linux and Windows, all supported browser engines, runtime audit and Linux performance budgets before deploying.

Independent security review, screen reader trials, physical phone keyboard/camera trials, human participants and field performance are NOT_RUN. Camera acquisition depends on HTTPS, browser support, permission and device availability. QR reading needs decoder assets to be available; no offline cache or service worker is promised.
